# Επαναχρησιμοποίηση καπνού χωρίς αλλαγή της εικόνας

Κάθε jump ή dash μπορεί να δημιουργήσει ένα table καπνού με εννέα πεδία:
θέση, ταχύτητα, υπόλοιπα υποπίξελ, sprite και δύο flags αναστροφής.
Παλαιότερα, όταν έληγε το animation, το table γινόταν σκουπίδι για τον
collector και το επόμενο εφέ δημιουργούσε καινούργιο.

Η `smoke_pool` είναι μια ιδιωτική λίστα από **ανενεργά** tables. Όταν ένα
σωματίδιο λήγει, αφαιρείται από τη λίστα σχεδίασης και μπαίνει εκεί. Η επόμενη
`effect_smoke()` παίρνει ένα διαθέσιμο table με `deli()` και ξαναγράφει όλα
τα πεδία του. Αν δεν υπάρχει διαθέσιμο table, δημιουργεί καινούργιο.
Δεν υπάρχει ανώτατο όριο στον καπνό και δεν παραλείπεται κανένα σωματίδιο.

Η σειρά της ενεργής λίστας παραμένει η σειρά δημιουργίας. Η σειρά των
ανενεργών tables δεν επηρεάζει την εικόνα, επειδή κανένα δεν σχεδιάζεται
και όλα τα πεδία του αντικαθίστανται πριν επιστρέψει στην ενεργή λίστα.
Κάθε δημιουργία καλεί ακριβώς τις ίδιες πέντε `rnd`, με την ίδια σειρά:
ταχύτητα, x, y, οριζόντια αναστροφή, κατακόρυφη αναστροφή.

Η `clear_smoke()` στο respawn επιστρέφει και τα ενεργά tables στην pool
πριν αδειάσει την ενεργή λίστα. Το νέο παιχνίδι, μέσω `initialize_effects()`,
αδειάζει και τις δύο λίστες. Δεν κρατιέται μόνιμα η κορυφαία κατανάλωση ενός
προηγούμενου run.

## Γιατί αυτό βοηθά κυρίως τα αργά frames

Στη native διαδρομή των 162 updates, ο median χρόνος ήταν σχεδόν ίδιος:
611.808 → 613.250 cycles. Δεν παρουσιάζουμε την pool ως γενική επιτάχυνση
κάθε frame. Το όφελος αφορά τις συνεχείς δεσμεύσεις μνήμης και τις αιχμές GC.

Σε χωριστό native workload, με ένα σωματίδιο ανά τρία updates και burst
οκτώ σωματιδίων κάθε 97 updates, συγκρίθηκαν τα ίδια πρώτα 800 updates:

| Μέτρηση | Νέο table κάθε φορά | Επαναχρησιμοποίηση |
| --- | ---: | ---: |
| Update p95 | 131.188 cycles | 53.265 cycles |
| Συνολικό frame p95 | 343.724 cycles | 267.181 cycles |
| Μέγιστο frame | 1.671.996 cycles | 884.495 cycles |
| Collections | 2 | 0 |
| Άθροισμα εργασίας, μετά τα πρώτα 20 updates | 186,5M cycles | 160,5M cycles |

Αυτό είναι περίπου 13,9% λιγότερη συνολική εργασία στο συγκεκριμένο
workload. Η πρώτη χρήση και ένα μεγαλύτερο burst εξακολουθούν να δεσμεύουν
νέα tables, ενώ άλλα συστήματα του παιχνιδιού εξακολουθούν να μπορούν να
προκαλέσουν GC. Η pool δεν εγγυάται ότι κάθε frame μένει στο budget.
Οι μετρήσεις έγιναν πριν από μεταγενέστερες βελτιώσεις του ίδιου του GC.

## Έλεγχος ότι δεν αλλάξαμε τον καπνό

```sh
python3 examples/celeste/tests/verify_smoke_pool.py
```

Το script δημιουργεί δύο προσωρινά projects. Το ένα χρησιμοποιεί την
παραγωγική pool και το άλλο την προηγούμενη απλή constructor. Και τα δύο
περνούν από τον κανονικό transpiler/TinyGo build. Δεν αλλάζει τα assets ή
το project του παιχνιδιού.

Συγκρίνονται 500 διαδοχικά snapshots: όλα τα πεδία κάθε ενεργού σωματιδίου,
η σειρά και το πλήθος τους, hash όλων των pixels και η επόμενη τιμή της
γεννήτριας τυχαιότητας. Ο έλεγχος προκαλεί moving GC κάθε 37 ticks,
respawn στο tick 170 και νέο παιχνίδι στο tick 340. Τα αποτελέσματα είναι
ακριβώς ίδια, χωρίς αριθμητική ανοχή. Το peak είναι 13 ενεργά σωματίδια.
Οι συγκρίσεις με το PICO-8 για κίνηση, animation και διάρκεια παραμένουν
στη χωριστή σουίτα presentation.
