# Imported PCM audio: mTile versus Butano, 30 FPS

Measured 2026-11-02. Read [the illustrated explanation](../../audio/imported-performance.md)
for the results and developer decisions. This directory retains the evidence
for **31 ROM/configuration combinations**, including diagnostic controls.
No production runtime or compiler optimization was made for these tests.

## Reproduce

Build the repository's normal pinned native player first. Install TinyGo,
devkitARM and a working `mmutil` which emits MAS **0x18** for devkitARM.
Pass a local Butano Git checkout containing the pinned revision. The harness
exports that commit into its own temporary directory; it does not modify
the source checkout or add stopwatch hooks to either engine.

```sh
python3 scripts/butano-bench/pcm/run.py \
  --butano /path/to/butano \
  --mmutil /path/to/mmutil \
  --work /private/tmp/mtile-pcm-compare-20261102 \
  --out docs/benchmarks/imported-audio-performance-2026-11-02

python3 scripts/butano-bench/pcm/report.py \
  docs/benchmarks/imported-audio-performance-2026-11-02 --compress
```

`--only mod4` selects matching labels; `--rebuild` replaces existing ROMs
and measurements. Use a fresh work/output directory after changing source
or measurement settings. Build logs, generated Lua/Go/C++, ROMs, ELF files,
link maps and generated targets remain under the selected work directory.
The report retains hashes and compressed measurement evidence, not binaries
for the whole toolchain.

The original test tones are generated by `assets()` in the harness:
1/4/16/32-channel MODs, a 0.5-second 8-bit mono 16 kHz WAV, and a
10-second 16-bit mono 22.05 kHz WAV. MOD notes retrigger every 16 rows,
using looped sine instruments at volume 8. WAV playback volume is 0.125
in both engines, avoiding clipping when eight copies overlap. The short
WAV is triggered every 30 game updates; the long WAV every 300. Both
engines receive identical converted banks, verified by SHA-256.
This matches the normalized volume command, not an exact integer gain:
mTile scales by 255, while Butano uses an eight-fraction-bit volume before
clamping to 255. Along with service phase, this prevents a claim of
sample-for-sample or exact loudness parity. The active voice counts and
nonzero mixer workloads are checked independently.

## Configuration

- Butano commit: `04374b034c76b82bfdc3aa6c38d652e5e7778a68`.
- mTile base: `00897dd13e5b34560cf654bba5e76cd16b2bb4c7`, **dirty checkout**
  containing the imported-audio feature. This is not a published commit.
  Per-ROM/ELF hashes are in `results.json`; `source-sha256.json` identifies
  relevant files at report generation time, not a historical clean checkout.
- TinyGo 0.42.0, LLVM 22.1.4, `-opt=2 -gc=none`, normal mTile flags.
- devkitARM release 65 / GCC 14.2.0, stock Butano `-O2` Thumb configuration,
  asserts/logging disabled, frame timer F/1, Maxmod enabled, unused DMG
  backend disabled. No LTO switch or compiler tuning was added.
- Primary mTile renderer: forced Mode 0, a direct `cls(0)` with no map,
  sprites or input. Butano uses a blank scene. Both update at every
  second LCD refresh. A separate Mode 4 control exposes bitmap-clear cost.
- Both PCM paths use Maxmod's standard 16 kHz mode: 264 samples per
  59.7275 Hz LCD refresh, approximately 15,768 Hz output, stereo FIFOs.
- Butano defaults: `MAX_MUSIC_CHANNELS=16`, `MAX_SOUND_CHANNELS=4`, which
  this backend sums to **20** module/active/mixer records.
- Matched Butano: 24 + 8 = **32** records, with 8 effect queue slots.
  The backend uses the sum for module and mixer capacity. The 32-voice
  stress case has no effects; active mixer records are inspected to prove
  all 32 voices are present. mTile uses 32 records and 8 effect slots.
- `off` uses a null audio backend in Butano and dead-stripped PCM in mTile.
  `idle` links and initializes PCM but plays nothing.

The converter used here was BlocksDS mmutil
`afd0270861d91d5a45ee92839b8047a48a008202`, built with
`MM_MMUTIL_DEVKITPRO_COMPAT`. Its executable hash is retained. Temporary
host-only build adaptations expanded upstream `#embed` data into numeric
arrays and supplied the missing `errors.h` include in that compatibility
branch. No conversion algorithms or generated bank contents were altered.
Normal users can use a working devkitPro converter directly.

## CPU accounting

Warm up for 60 game updates, align to a new complete GLUD publication,
then profile **300 complete game-update intervals**. This spans at least
one complete repeating MOD pattern. Two independent **600-update captures**
per ROM check cadence, PCM output and memory telemetry after the same
warmup. Both captures are deterministic in the pinned emulator.

The native profiler steps ARM/Thumb instructions in the unmodified ROM.
Pending hardware events are processed separately before each instruction.
Every measured cycle reconciles exactly:

```text
elapsed = instruction cycles + non-HALT event advancement + HALT event advancement
work    = instruction cycles - deliberate wait instruction cycles
```

DWARF inline frames classify the timer/display polling loops and Butano's
VBlank wait. BIOS/other addresses remain included in instruction totals.
Size-zero assembly labels are retained for mixer attribution.

`profile.cpu` is **non-wait instruction work**. DMA/event advancement is
excluded from that primary metric for both engines: mGBA folds idle
hardware scheduling into a long HALT advance, whereas it exposes separate
stalls during mTile's polling. Adding only non-HALT events to one engine
would bias a close comparison. `cpuWithNonHaltEvents` retains that additional
accounting view explicitly; it is not a fully symmetric total-DMA metric.
For four voices, this second view is 66,765 cycles for mTile and 64,051
for matched Butano. The primary instruction-work figures are 64,932 and
63,830. Neither view is an electrical-power measurement.

Instruction work includes debug publication. The mTile mailbox has more
fields than this minimal Butano publisher, so these are instrumented-program
results. Both no-audio floors are supplied. The fixture uses normal public
audio APIs; neither the main-loop `stat(1)` value nor Butano's timer result
is used to rank audio CPU cost.

For the 32-voice diagnostic, the profiler also recognizes `mmFrame` entry
and its return address, observing its full emulated duration. mTile had
601 calls during 300 publication intervals because one interval slipped
an extra refresh; Butano had 600. That extra service also affects the
per-game-update CPU total. The reported 197,120-cycle threshold is the
duration of 160 LCD scanlines, not a universal deadline for all backends.

## Memory and controls

ELF sections and symbols separate EWRAM, IWRAM code/data, and reserved
stacks. EWRAM totals use the application static end and exclude the shared
512-byte mailbox. Butano's ELF has an additional 8-byte padding section;
it is retained in raw sections but not its static allocation figure.
No data is inferred from host emulator RAM usage.

Butano's benchmark mailbox repurposes four generic heap fields for
`used_static_ewram`, `used_static_iwram`, current stack depth and
`used_alloc_ewram`. The adapter decodes these as **Butano memory**, never
as Lua heap capacity. In all captured publications its dynamic EWRAM
allocation was zero. That sampled observation alone would not prove that
a transient allocate/free pair can never occur; the PCM engine's fixed
buffers and direct initializer are also inspected in source.

For mTile, the emitted normal cartridge has no Lua heap semispaces and no
linked allocation/collection path in the audio-only program. Telemetry
shows zero capacity/allocation/live bytes/collections/errors. Stack depth
is sampled on every profiled instruction by CPU mode and compared with
linker stack tops. It excludes startup before warmup and is not a general
proof of worst-case stack bounds.

Diagnostic controls modify **temporary runtime copies only**:

1. `mtile-heap-control`: retains the Lua heap through the existing build
   switch. Two 57,344-byte semispaces plus larger context storage add
   143,064 B EWRAM without causing playback allocations or collections.
2. `mtile-cap20-control`: changes 32 channel records to 20 and effect
   capacity from 8 to 4. The four-voice song still plays. It saves exactly
   1,008 B EWRAM and about 1,477 work cycles per update. This is diagnostic,
   not a new user-facing project setting.
3. `mtile-mode4`: keeps production PCM but clears a bitmap screen. Mixer
   attribution is unchanged; extra drawing is not called audio overhead.
4. `mtile-line16-control`: changes only the VCOUNT service from line 0 to
   line 16. Both 600-update captures lose the 32-voice cadence gap with
   essentially unchanged CPU and memory. No production scheduling change
   was shipped. Renderer transfer timing must be validated before adoption.

The normal 32-voice case has gaps `{2: 598, 3: 1}` in each capture, versus
`{2: 599}` for matched Butano and the line-16 control. The existing missed
counter does not increase over this capture interval, so the independent
cadence trace is necessary. All other normal cases have two-refresh gaps.
Captured PCM is non-silent when expected, with zero reported buffer
overflow and zero clipped 16-bit samples. Identical soundbanks do not
establish sample-for-sample output parity: playback phases differ, and
these checks do not replace physical-hardware listening tests.
