Assembly mechanism (same preserved generated Go, only runtime changed):

The baseline hashFind enters __aeabi_uidivmod unconditionally after computing
the numeric hash. That helper calls __udivmodsi4 -> __aeabi_uidiv, which uses
two software count-leading-zero calls and a long-division loop. The workload
does 64 reads and 64 updates of existing hash keys every tick: 128 divisions.

Baseline excerpt:
  08002314: mov r0, r2
  08002318: bl __aeabi_uidivmod

The candidate tests capacity & (capacity - 1), uses AND for power-of-two
capacity 64, and only calls the divider on the other branch. Non-power-of-two
table capacities retain exact modulo behavior.

Candidate excerpt:
  08002308: sub r6, r5, #1
  0800230c: tst r5, r6
  08002310: bne 08002334
  08002314: and ip, r6, r2
  08002318: b 0800235c
  ...
  08002348: bl __aeabi_uidivmod

This removes 128 executed software divisions per steady-state workload tick;
the divider remains linked for fallback and other operations. The measured
runtime-only comparison is recorded separately in numeric-hash-bucket-target.txt.
